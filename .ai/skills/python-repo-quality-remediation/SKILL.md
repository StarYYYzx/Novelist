# Python 仓库质量整治（分批闭环）

## 0. 铁律：批次顺序 = 真 bug → 代码卫生 → **文档最后**

文档基线里通常写着"src 行数 / 文件数 / 测试数"这类数字。**若先刷文档再删死代码和导入，数字立刻又失效**，
文档白改一遍。所以顺序固定：

1. **批次一 · 真 bug**：语法错误、未定义名、静默失效的测试、环境依赖导致的假失败
2. **批次二 · 代码卫生**：lint 清零、死代码、调试脚本归位
3. **批次三 · 文档口径**：基线重测 + 跨文档硬矛盾 + 目录树/结构图对齐源码

每批：**改动 → 全量回归绿 → 单独提交**。用户没说推送就不要 push（问过的就按答复做）。

## 1. 开工前必做

- **打回滚锚点**：`git tag pre-<task>-<date>` 指向当前提交，并告知用户回滚命令。
  （本机 `git status` 可能显示 `[gone]`——先确认是不是环境假象，别当成远端丢分支。）
- **确认测试怎么跑**：解释器路径、是否要带环境变量、慢测试是否默认跳过。
  某些沙箱会因"删除文件数超阈值"误杀测试进程，需显式关掉（见 §5）。
- **先取 lint 基线**：`ruff check <src> <tests> --output-format=json`，用脚本按规则码归类计数。
  比 `--statistics` 更好用，便于逐条判定。

## 2. 用"精确文本替换脚本"做批量定式修改

并行改几十处时，逐条 Edit 太慢、`sed` 又不可审计。写一次性 Python 脚本，**每条替换都断言命中唯一**：

```python
PATCHES = [(path, old, new), ...]
for path, old, new in PATCHES:
    text = io.open(path, encoding="utf-8").read()
    n = text.count(old)
    if n != 1:
        print(f"!! SKIP {path} 命中 {n} 次: {old[:60]!r}")
        continue
    io.open(path, "w", encoding="utf-8", newline="\n").write(text.replace(old, new))
```

- 命中数 ≠ 1 就**跳过并打印**，然后补更长的锚点（含函数名/相邻行）重跑第二轮。
  这是特性不是缺陷——它拦住了误伤。实践命中率：28 条里 2 条因锚点太泛被正确拦下。
- 写入用 `newline="\n"`，避免 CRLF 抖动。
- 脚本用完即删。
- 大块替换（整节文档）按**行区间**替换：先断言区间首尾行的内容再切片拼接，比匹配整段文本稳。

## 3. ruff 两个必踩的陷阱

### 3.1 `F841 --fix --unsafe-fixes` 会留下无意义表达式
对"无副作用右值"（`x = d[k]`、`x = set(...)`、`x = bp.section(...)`），ruff 只删赋值、**保留右值独立成句**；
对 `spy = lambda ...` 甚至留下一个裸 lambda。所以：

- **先 `--diff` 预览**，不要直接 `--fix --unsafe-fixes`。
- 无副作用右值 → **整行删除**。
- 有副作用调用（`run_shell(...)`、`update_from_chapter(...)`、`warmup_entities(...)`）→ 保留裸调用、只去赋值。

### 3.2 `F811` / `F841` 是"静默失效测试"的雷达
- `F811` 重复定义同名 `test_*` → **前一个用例永不执行**。必查。
- `F841` 在测试里 = "赋了值却从不断言" → 用例可能形同虚设。
  典型：`called = []; spy = lambda ...` 但 spy 从未传入，`assert not called` 恒真。
  修法不是删变量，而是**用 monkeypatch 把探针真正接上**，让断言有意义。

## 4. 删导入前必须查重导出

ruff 只看得见本文件的使用。删 `from .x import A` 前，全库搜索 `from <module> import A` 与 `import A`，
确认消费者都是从**源模块**导入而非经此中转。否则会静默破坏公共 API。

`__init__.py` 里的 F401 多半是**有意重导出** → 正解是补进 `__all__`，而不是删导入。

## 5. 环境适配

- **解释器/包缺失**：优先用仓库既定的解释器；若 `ModuleNotFoundError`，先看是否被清空过 site-packages。
- **流式输出被污染**：stdout 混入框架日志时，`pytest -q > _out.txt 2>&1` 写文件后 Read 文件。
- **shell 工具缺失**（Windows 沙箱常见 `head/tail/cat/dirname/wc/find` 全部 not found）：
  一律改用 `<python> -c "..."` 做统计与过滤，别写 shell 管道；删临时文件用 `os.remove`。
- **测试进程被误杀**：某些环境按"删除文件数"拦截，跑全量前显式关闭该机制。

## 6. 边界：哪些"死代码"不该删

零引用 ≠ 该删。**先查文档**：若设计文档明确记载某模块是"已备工具、尚未接入"的**预留件**，
删它等于改设计，需要用户拍板，不能当卫生问题顺手清掉。

筛查方法：在 `docs/` 里 grep 该文件名，看是否有"未落地 / 待接入 / 已就绪未接入"之类表述。

## 7. 文档口径怎么修才不越界

- **只改"当前基线"类声明**（README 的测试数、命令手册的 baseline、指南的"当前回归结果"）。
- **不要改历史记录**：里程碑日志里的"全量 774 passed"是**当时实况**，改了就是造假。
  判断法：看该数字附近是否有日期/提交号/里程碑编号，有 = 历史记录。
- 重测基线时保留"旧值 vs 新值"双列，让读者看到演化方向，比只写新值更有用。
- 目录树/结构图要么删掉前瞻条目，要么**加一张"原图条目 → 实际落点"对照表**（后者信息量更大）。
- 同一个事实在 N 处出现时，全部统一，并顺手写清"以哪一处为准"。

## 8. 收尾清单

- [ ] `ruff check <src> <tests> <scripts>` 全绿
- [ ] 全量回归绿，并记录**收集数 / passed / skipped / deselected** 四个数（口径要能对账）
- [ ] 跨文档矛盾复扫：ADR 编号、测试数、开关默认值、目录树
- [ ] 审计/整治报告补一节"修复进展"，逐条对账原报告的行动项（含"刻意未做 + 原因"）
- [ ] 临时脚本与输出文件清理干净
- [ ] 项目记忆：更新长期约定 + 追加当日日志（记"可复用的教训"而非过程流水）
