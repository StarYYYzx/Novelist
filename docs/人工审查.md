# 第二批 · 讨论与结论

> 以下为执行侧对两条建议的实测核对、分析与结论。
> 讨论依据：本地 LM-Studio `qwen/qwen3.5-9b`（9B，约 20 token/s）上的端到端实测，
> 复现脚本见 `novel_workspace/_harness/probe_thinking_off.py`、`probe_budget2.py`。

## 第 1 条：max_token 的设计是否合理？

### 实测证据

| 场景 | system prompt | max_tokens | 结果 |
| --- | --- | --- | --- |
| 裸调用 | — | 200 | 正文 **0 字**，思考 695 字（`reasoning_tokens=200`，`finish_reason=length`） |
| 裸调用 | — | 300 | 正文 **0 字**，思考 863 字（`reasoning_tokens=300`） |
| v1 旧链路 | 一句话 | 800–1500 | 10/10 章产出正文，614–1523 字 |
| v2 新链路（圣经注入） | 1008 字 | 1400 | **10/10 章正文 0 字**，全部失败 |
| v2 后段 | 1008 字 | 1600 / 2000 | HTTP 400：`ErrorOutOfDeviceMemory`，随后模型彻底无法加载（需约 16.80 GB） |

尝试关闭思考的三种方式——`chat_template_kwargs:{enable_thinking:false}`、顶层
`enable_thinking:false`、prompt 追加 `<arg_key:6124c78e>`——**在 LM-Studio 上均无效**，仍然输出思考。

### 分析

问题不在"预算给小了"，而在**预算的语义错了**，具体两处：

**（a）预算是"总输出预算"，不是"正文预算"。**
`qwen3.5-9b` 是思考型模型，推理过程以 `reasoning_content` 返回，**计入 `max_tokens`**。
我们把它当成"正文能写多少字"来配，实际被思考先吃掉一大半。
prompt 越长 → 思考越长 → 留给正文的越少。圣经注入把 system prompt 从一句话拉到 1008 字，
思考随之变长，1400 的预算直接被吃光，正文 0 字。
**后果不是"质量下降"，而是整章空输出**——`produce_chapter` 只判断 `len(final) < 20`
就抛错，一章都写不出来。

**（b）唯一补救手段会把本地机器挤爆。**
既然思考挤占预算，直觉解法是加大预算；但加大预算后 KV cache 暴涨，实测 1600 就
`ErrorOutOfDeviceMemory`，随后模型连加载都失败。
**两个约束从两头夹击：预算小了出不了正文，预算大了显存溢出。**
"一次生成一整章"这个做法在本地 9B 上被夹死了。

**（c）截断后没有续写机制。**
`finish_reason == "length"` 时（被预算截断），当前实现把半成品按"不合格"处理，
走带修复提示的整章重生成——已经在做（B-04），但**重来一遍比续写贵得多**，
且重来时思考开销要再付一次。

### 结论

**不合理，建议修。** 三层修复，按优先级：

1. **适配器层（必要）**：`providers/lmstudio.py` 识别 `reasoning_content` 与
   `completion_tokens_details.reasoning_tokens`，把"正文预算"与"思考预算"分开计量；
   当 `finish_reason == "length"` 且正文过短时，**自动提高预算重试**（而不是直接判定失败）。
2. **生成层（必要）**：`finish_reason == "length"` 时做**续写**——把已生成内容作为前缀
   继续生成，而不是整章重来。
3. **编排层（结构性解法，见第 2 条）**：把生成单位从"章"降到"事件"，单次输出目标变小，
   从根上缓解两头夹击。

### 待办

- [ ] `providers/lmstudio.py` 支持 reasoning 计量与预算自适应重试
- [ ] `produce_chapter` 支持 `finish_reason == "length"` 时续写
- [ ] 配置项区分 `max_tokens`（总）与 `max_content_tokens`（正文）
- [ ] 环境：LM-Studio 当前因系统资源不足无法加载 9B 模型，需释放内存或降低上下文设置后
      才能继续 v2 生成

## 第 2 条：深度优先递归拆解结构

### 与当前实现的对照

| 维度 | 你的设想 | 当前实现 |
| --- | --- | --- |
| 最小生成单位 | 事件 | **章**（一次调用产出整章） |
| 回写时机 | 每个事件写完立即回写 | **整章写完后**，由编纂员从成文里反抽事件再回写 |
| prompt 内容 | 当前事件始末 + 参与人物 | 整章细纲（含全部 key_events）+ 全部出场人物 |
| 拆解方式 | LLM 递归判断"是否单一事件" | 不拆解 |

**关键发现：当前实现本来就偏离了设计文档。**
docs/05 §5.4 与 ADR-013 规定的是「正文每个**事件**落定即触发实时回写」，
而 `produce_chapter` 只在章末回写一次——这是我在 M3d 测试报告里记为 B-03 的缺口，
`core/chronicler.py` 只补上了"抽取真实事件"，**没补上"按事件粒度驱动生成"**。
所以你的设想不是在改设计，是在把实现拉回设计。

另一个事实：**大纲里已经声明了事件**。
`outline/chapters/<vol>-<ch>.md` 的 front-matter 有 `key_events: [...]`（本测试项目每章 2–4 个）。
也就是说，事件清单是现成的，不需要 LLM 去猜"这一段是不是一个事件"。

### 合理性分析

**成立的部分（采纳）**

- 与 ADR-013 一致，是设计文档原本的意思。
- **正好是第 1 条的结构性解法**：单次输出目标从"一整章"降到"一个事件"，
  预算压力与显存压力同时下降。两条建议是同一个问题的两面。
- 章内后续事件写作时，可以"先忆"到**上一个刚回写的事件**——当前做不到，
  本章的事件要等本章写完才入库，章内一致性只能靠模型窗口硬撑。
- 事件粒度天然可断点续写，符合 NFR-3。
- 契合"用写代码的方式写小说"：相当于按函数逐个实现并即时 commit，
  而不是一次写完整个文件再提交。

**代价与风险（需要约束）**

- **调用次数翻倍**：每章 2–4 个事件 → 调用数 ×2~4，9B 模型上是数倍时间。
- **思考开销是按次付的**：实测一次调用思考 600–900 字。事件切得越细，
  思考占比越高，**单位字数成本反而上升**。所以不能无限细分。
- **接缝连贯**：事件之间会读起来像片段拼贴，需要过渡处理。
- **递归判断本身要 LLM 调用吗？** 如果要，成本再加一层，且判断可能不稳。

### 结论

**采纳，但落地方式做两点调整：**

**调整一：用「声明式事件清单」替代「LLM 递归判断拆解」。**
`key_events` 已经写在大纲里，直接按它迭代即可，省掉一整层 LLM 判断；
只在 `key_events` 缺失时才回退为整章生成。
"递归拆解"保留为**大纲层**的能力（卷 → 章 → 事件的层级本来就有），
不必下沉到生成期的运行时判断。

**调整二：每章事件数设上限（建议 2–3 个），不做无限细分。**
理由就是上面的思考开销——细分的边际收益会被按次付的思考成本吃掉。

**建议的落地形态：`事件循环`（`produce_chapter` 改造）**

```
for each key_event in 细纲.key_events:      # 深度优先，串行
    1. 先忆：query_memory(当前事件 + 参与人物)
    2. 装配：本事件始末 + 参与人物卡 + 上一事件末尾 200–300 字（接缝上下文）
    3. 生成：单次输出目标 = 一个事件（约 300–600 字）
    4. 完整性校验：截断则续写（第 1 条的修复）
    5. 回写：Chronicler 提炼本事件 → 冲突双检 → 落 memory + 增量索引
    6. 追加到本章草稿文件
所有事件完成后 → 整章级：一致性规则检 + 审校师语义检 + 文风润色
```

接缝处理：每个事件的 prompt 带上**上一事件末尾 200–300 字**，让模型接着写，
避免片段拼贴感。

### 待办

- [ ] `produce_chapter` 改为事件循环（声明式 `key_events` 驱动）
- [ ] 事件级 prompt 装配：本事件 + 参与人物 + 上文接缝
- [ ] 每个事件写完即回写（真正落地 ADR-013）
- [ ] 约束：每章事件数上限、单事件最小篇幅，防拆解失控
- [ ] `key_events` 缺失时回退整章生成（降级路径）

### 需要你拍板的两点

1. **时间成本**：事件循环下，10 章 × 3 事件 ×（生成+编纂+润色）在本地 9B 上估计
   **3–5 小时**（当前链路约 1.5 小时）。是否接受？或者只在关键章（重场戏）启用事件粒度，
   其余章仍用整章生成？
2. **润色粒度**：文风润色放在"每个事件之后"还是"整章拼完之后"？
   我倾向**整章之后**——事件粒度润色会破坏章内节奏的整体性，且成本翻倍。
