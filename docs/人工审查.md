# 第二批 · 讨论与结论

> 以下为执行侧对两条建议的实测核对、分析与结论。
> 讨论依据：本地 LM-Studio `qwen/qwen3.5-9b`（9B，约 20 token/s）上的端到端实测，
> 复现脚本见 `novel_workspace/_harness/probe_thinking_off.py`、`probe_budget2.py`。

## 第 1 条：max_token 的设计是否合理？

### 实测证据

| 场景 | system prompt | max_tokens | 结果 |
| --- | --- | --- | --- |
| 裸调用 | — | 200 | 正文 **0 字**，思考 695 字（`reasoning_tokens=200`，`finish_reason=length`） |
| 裸调用 | — | 300 | 正文 **0 字**，思考 863 字（`reasoning_tokens=300`） |
| v1 旧链路 | 一句话 | 800–1500 | 10/10 章产出正文，614–1523 字 |
| v2 新链路（圣经注入） | 1008 字 | 1400 | **10/10 章正文 0 字**，全部失败 |
| v2 后段 | 1008 字 | 1600 / 2000 | HTTP 400：`ErrorOutOfDeviceMemory`，随后模型彻底无法加载（需约 16.80 GB） |

尝试关闭思考的三种方式——`chat_template_kwargs:{enable_thinking:false}`、顶层
`enable_thinking:false`、prompt 追加 `<arg_key:6124c78e>`——**在 LM-Studio 上均无效**，仍然输出思考。

### 分析

问题不在"预算给小了"，而在**预算的语义错了**，具体两处：

**（a）预算是"总输出预算"，不是"正文预算"。**
`qwen3.5-9b` 是思考型模型，推理过程以 `reasoning_content` 返回，**计入 `max_tokens`**。
我们把它当成"正文能写多少字"来配，实际被思考先吃掉一大半。
prompt 越长 → 思考越长 → 留给正文的越少。圣经注入把 system prompt 从一句话拉到 1008 字，
思考随之变长，1400 的预算直接被吃光，正文 0 字。
**后果不是"质量下降"，而是整章空输出**——`produce_chapter` 只判断 `len(final) < 20`
就抛错，一章都写不出来。

**（b）唯一补救手段会把本地机器挤爆。**
既然思考挤占预算，直觉解法是加大预算；但加大预算后 KV cache 暴涨，实测 1600 就
`ErrorOutOfDeviceMemory`，随后模型连加载都失败。
**两个约束从两头夹击：预算小了出不了正文，预算大了显存溢出。**
"一次生成一整章"这个做法在本地 9B 上被夹死了。

**（c）截断后没有续写机制。**
`finish_reason == "length"` 时（被预算截断），当前实现把半成品按"不合格"处理，
走带修复提示的整章重生成——已经在做（B-04），但**重来一遍比续写贵得多**，
且重来时思考开销要再付一次。

### 结论

**不合理，建议修。** 三层修复，按优先级：

1. **适配器层（必要）**：`providers/lmstudio.py` 识别 `reasoning_content` 与
   `completion_tokens_details.reasoning_tokens`，把"正文预算"与"思考预算"分开计量；
   当 `finish_reason == "length"` 且正文过短时，**自动提高预算重试**（而不是直接判定失败）。
2. **生成层（必要）**：`finish_reason == "length"` 时做**续写**——把已生成内容作为前缀
   继续生成，而不是整章重来。
3. **编排层（结构性解法，见第 2 条）**：把生成单位从"章"降到"事件"，单次输出目标变小，
   从根上缓解两头夹击。

### 待办

- [x] `providers/lmstudio.py` 支持 reasoning 计量与预算自适应重试
- [x] `produce_chapter` 支持 `finish_reason == "length"` 时续写
- [ ] 配置项区分 `max_tokens`（总）与 `max_content_tokens`（正文）
- [ ] 环境：LM-Studio 当前因系统资源不足无法加载 9B 模型，需释放内存或降低上下文设置后
      才能继续 v2 生成

## 第 2 条：深度优先递归拆解结构

### 与当前实现的对照

| 维度 | 你的设想 | 当前实现 |
| --- | --- | --- |
| 最小生成单位 | 事件 | **章**（一次调用产出整章） |
| 回写时机 | 每个事件写完立即回写 | **整章写完后**，由编纂员从成文里反抽事件再回写 |
| prompt 内容 | 当前事件始末 + 参与人物 | 整章细纲（含全部 key_events）+ 全部出场人物 |
| 拆解方式 | LLM 递归判断"是否单一事件" | 不拆解 |

**关键发现：当前实现本来就偏离了设计文档。**
docs/05 §5.4 与 ADR-013 规定的是「正文每个**事件**落定即触发实时回写」，
而 `produce_chapter` 只在章末回写一次——这是我在 M3d 测试报告里记为 B-03 的缺口，
`core/chronicler.py` 只补上了"抽取真实事件"，**没补上"按事件粒度驱动生成"**。
所以你的设想不是在改设计，是在把实现拉回设计。

另一个事实：**大纲里已经声明了事件**。
`outline/chapters/<vol>-<ch>.md` 的 front-matter 有 `key_events: [...]`（本测试项目每章 2–4 个）。
也就是说，事件清单是现成的，不需要 LLM 去猜"这一段是不是一个事件"。

### 合理性分析

**成立的部分（采纳）**

- 与 ADR-013 一致，是设计文档原本的意思。
- **正好是第 1 条的结构性解法**：单次输出目标从"一整章"降到"一个事件"，
  预算压力与显存压力同时下降。两条建议是同一个问题的两面。
- 章内后续事件写作时，可以"先忆"到**上一个刚回写的事件**——当前做不到，
  本章的事件要等本章写完才入库，章内一致性只能靠模型窗口硬撑。
- 事件粒度天然可断点续写，符合 NFR-3。
- 契合"用写代码的方式写小说"：相当于按函数逐个实现并即时 commit，
  而不是一次写完整个文件再提交。

**代价与风险（需要约束）**

- **调用次数翻倍**：每章 2–4 个事件 → 调用数 ×2~4，9B 模型上是数倍时间。
- **思考开销是按次付的**：实测一次调用思考 600–900 字。事件切得越细，
  思考占比越高，**单位字数成本反而上升**。所以不能无限细分。
- **接缝连贯**：事件之间会读起来像片段拼贴，需要过渡处理。
- **递归判断本身要 LLM 调用吗？** 如果要，成本再加一层，且判断可能不稳。

### 结论

**采纳，但落地方式做两点调整：**

**调整一：用「声明式事件清单」替代「LLM 递归判断拆解」。**
`key_events` 已经写在大纲里，直接按它迭代即可，省掉一整层 LLM 判断；
只在 `key_events` 缺失时才回退为整章生成。
"递归拆解"保留为**大纲层**的能力（卷 → 章 → 事件的层级本来就有），
不必下沉到生成期的运行时判断。

**调整二：每章事件数设上限（建议 2–3 个），不做无限细分。**
理由就是上面的思考开销——细分的边际收益会被按次付的思考成本吃掉。

**建议的落地形态：`事件循环`（`produce_chapter` 改造）**

```
for each key_event in 细纲.key_events:      # 深度优先，串行
    1. 先忆：query_memory(当前事件 + 参与人物)
    2. 装配：本事件始末 + 参与人物卡 + 上一事件末尾 200–300 字（接缝上下文）
    3. 生成：单次输出目标 = 一个事件（约 300–600 字）
    4. 完整性校验：截断则续写（第 1 条的修复）
    5. 回写：Chronicler 提炼本事件 → 冲突双检 → 落 memory + 增量索引
    6. 追加到本章草稿文件
所有事件完成后 → 整章级：一致性规则检 + 审校师语义检 + 文风润色
```

接缝处理：每个事件的 prompt 带上**上一事件末尾 200–300 字**，让模型接着写，
避免片段拼贴感。

### 待办

- [x] `produce_chapter` 改为事件循环（声明式 `key_events` 驱动）
- [x] 事件级 prompt 装配：本事件 + 参与人物 + 上文接缝
- [x] 每个事件写完即回写（真正落地 ADR-013）
- [ ] 约束：每章事件数上限、单事件最小篇幅，防拆解失控
- [x] `key_events` 缺失时回退整章生成（降级路径）

### 需要你拍板的两点

1. **时间成本**：事件循环下，10 章 × 3 事件 ×（生成+编纂+润色）在本地 9B 上估计
   **3–5 小时**（当前链路约 1.5 小时）。是否接受？或者只在关键章（重场戏）启用事件粒度，
   其余章仍用整章生成？
2. **润色粒度**：文风润色放在"每个事件之后"还是"整章拼完之后"？
   我倾向**整章之后**——事件粒度润色会破坏章内节奏的整体性，且成本翻倍。

# 第三批 · 讨论与结论

> 背景补充：第二批讨论后，修复已落地并**完成了 v2 全 10 章生成**
> （AI 味均值 38.63→26.06、告警 3→0、30 条真实事件由系统编纂员产出、
> 全章完整收尾/零元叙事/零造人），评阅见 `_harness/v2评阅报告.md`。
> v2 暴露的新短板（跨章战力跳级、章间时间线错位、9B 审校师漏报跨章逻辑）
> 正是下面两条讨论要解决的结构问题。

## 第 1 条：章节划分——先细化成标题逐章写，还是一气呵成再按篇幅切？

### 结论

**章边界必须是规划出来的（前者），但细化要停在「章级细纲」，不要细到逐事件写死段落。**
"一气呵成再切章"在长篇上是**伪选项**。

### 论证

"一气呵成"只在**一次性能生成完的篇幅**里成立。一卷 8 万字 ≈ 12 万 token，
任何模型都装不下——所以它必然退化成"分多次续写"；续写时若没有规划好的章结构，
就是盲写：切分点交给运气。

| 维度 | 一气呵成再切 | 先定标题再逐章写 |
| --- | --- | --- |
| 伏笔管理 | 只能**事后反推**落点，`report_deadline` 无从承诺 | 规划期对齐 |
| 记忆锚点 | `at: {vol, ch}` 不确定 → 索引/先忆全乱 | 章边界先定，检索有稳定锚点 |
| 商业章约束 | 按篇幅切常落在场景中间；要切好仍需 LLM 判断卡点，成本回到前者还多一次全文重读 | `turns` 规划期设计 |
| 可恢复性 | 5 万字断了重试代价大 | 第 8 章标题细纲还在，接着写 |
| 人工审查介入点 | 成文后才能审 | 大纲/细纲层就能拦，错误在最便宜的阶段修 |

### 但前者有个真问题，不在"要不要标题"

**细化到哪一层停。** v1 实测暴露过：细纲把事件写成了句子，模型生成时照抄细纲、叙事干瘪。
所以规划期只定**结构**（标题、key_events、turns、threads_involved），不定**文句**——
文句是生成期的事，细纲不越权。

第二个真问题：**细纲会僵化**。写到第 6 章发现第 3 章埋的伏笔有更好的走向，细纲已定死。
解法见"滚动细纲"。

### 建议的分层

| 层 | 谁定 | 粒度 |
| --- | --- | --- |
| 卷→章（标题、边界） | 规划期，一次定 | 章级，预声明全部章 |
| 章内事件顺序 | 细纲 `key_events` 声明 | 2–4 个/章，**不写死文句** |
| 章内叙事 | 生成期 | 按 key_events 逐事件推进、逐事件回写 |
| 文句 | 生成期 | 模型自由 |

### 补充：滚动细纲

章标题/边界一次定死（伏笔承诺需要），但**未写章的 key_events 可被成文反馈修正**
（比如第 5 章实际把枯木长老写成偏帮主角，第 6–10 章细纲里他的立场就跟着调）。
这是网文作者的真实工作方式（写几章改一次大纲）。需要给大纲层加"细纲修订"能力，目前没有。

## 第 2 条：单事件展开——人设一股脑直出，还是多 agent 角色卡即兴 + 总结？

### 结论

**不是二选一。围读会的产出不能直接成为小说——它最终仍要一次"叙事化重写"，
而那一步就是"塞人设让 AI 编"。所以围读会只能是直出的前置增强；默认直出，重场戏才上受控版。**

### 围读会的致命伤：总结损耗

多 agent 即兴的产出是**对白素材**，不是小说文本。转成叙述时极易写成
"苏晚说……赵虎冷笑反驳……"的流水账，**丢掉对白的生动性**。
而这次叙事化重写本身仍需要人设/文风/视角约束——即 A 的形态。
所以 B = A + 一层昂贵的即兴预演，不是替代关系。

### 三档落地（不是二选一）

| 档 | 做法 | 调用次数 | 什么时候用 |
| --- | --- | --- | --- |
| 1 直出 | 人设+文风+纪律塞 system prompt，一次成章（现状） | 1 | 默认。过场、动作、单人戏 |
| 2 **剧本草稿** | 一次调用先以剧本体写对白交锋，第二次叙事化成小说 | 2 | 重场戏。多声音质感↑，无失控风险 |
| 3 受控围读会 | 真·多 agent，各持角色卡，主持人调度 + 结束判据 + 回合上限 | N×R+总结 | 需要**真信息不对称**时 |

**档 2 是关键中间态**：影视编剧本就这么干。它拿到围读会最想要的东西——
**角色声音的区分度**——成本仅 ×2，无失控风险，且 9B 也能跑。

### 档 3 的不可替代性只有一条

**agent 真的不知道对方的底牌。** 剧本草稿里模型全知，写不出信息差带来的真实错愕。
所以围读会只在这些场景值得：高潮对峙/多方博弈、关系转折点，
以及作为**探索工具**（不确定角色会怎么反应时让他自己说，产出喂回细纲，不直接成文）。

### 与现有设计的对齐

正是 docs/05 已规划、尚未接线的 ADR-012（角色演员 `write_take`，排演→整合）
与 ADR-014（受控围读会；SceneBus 与 join/say/leave 已就绪，
**缺主持人调度与结束判据**）。第一批审查第 3 条"join/exit 工具权限"的直觉是对的——
自由群聊必须收敛成受控排演，否则演嗨了推不动 key_event。

### 9B 的现实约束

9B 做演员角色扮演能力不足，即兴易出戏（现代腔/OOC/抢戏）。建议：
1. 先做档 2，只对细纲标记为重场戏的章启用（收益/成本比最好）；
2. 围读会按 ADR-014 做受控版，定位"探索 + 对白素材"，产出**不直接进正文**；
3. 加**对白区分度**度量（各角色平均句长/语气词/句式分布方差），量化档 2 是否真的比档 1 声音更分明。

## 第 3 条：做一个纯命令行修仙游戏，让 AI 扮演不同玩家去玩，再把游戏日志编撰成小说？

### 结论

**思路的内核是对的——"把一致性交给确定性系统"；但载体不该是游戏，而是一个轻量的
「世界状态层」。做游戏的话，编撰损耗会吃掉全部收益。**

### 这个思路真正吸引人的三点（都是真的）

- **硬一致性**：境界/物品/位置由引擎状态机保证，不会出现 v2 评阅里的"战力跳级"
  （ch2 被赵虎按进泥里、ch3 一招断腕）——这正是规则引擎和 9B 审校师都没拦住的。
- **不确定性**：RNG 让情节不可预测，缓解"AI 写得太顺"。
- **自主性**：agent 在规则世界里自己行动，可能涌现出规划外的合理情节。

### 三个硬伤

**1. 叙事密度（最致命）。** 游戏日志是"操作-反馈"记录：

```
> 打坐          你盘膝而坐，灵气缓缓入体。修为 +10
> 前往藏经阁     你走了半个时辰，到达藏经阁
```

小说需要动机、冲突、感官细节、人物弧线。日志天然低叙事密度——大量操作是
移动/等待/重复修炼，在小说里是一句话甚至跳过。筛选比例可能达到 10:1，
而"筛选"本身成本极高。

**2. 玩家激励与叙事目标错位。** agent 玩家的最优策略是"刷"（升级、囤资源、比价），
因为游戏激励如此；而"刷"在小说里是垃圾内容。要 agent 按人设行动，
等于把角色卡装进 agent——那就回到了围读会方案，游戏只是给 SceneBus 加了状态记录。

**3. 状态→叙事的映射缺口。** 游戏能保证"发生了什么"（what），
小说的灵魂是"怎么发生的、对人物意味着什么"（how/why）。从
"灵石 +50、修为突破"到"在哪儿、和谁、什么冲突、心理如何变化"——
这个映射就是**写作本身**，是全系统最难的部分，游戏引擎帮不上。

### 正确的内核形态：世界状态层（World State）

游戏引擎的本质是**确定性状态机 + 规则引擎**。本系统需要它解决的问题只有：
**可数值化的状态别让 LLM 记**。而这不需要做游戏——

- 新增 `bible/worldstate.json`：每个人物的 当前修为 / 所在位置 / 持有物 / 伤势 / 关系现值
- 事件回写时由编纂员同步更新——`MemoryWriter.append_experience` 的 **`state_delta`
  字段已在 schema 里预留，当前传 None，接口现成**
- 生成时把"当前状态"注入圣经上下文（谁在哪、什么修为、带什么伤）
- 一致性引擎加 **R-STATE**：正文写"苏晚以筑基期修为"但 worldstate 记录炼气三层 → block

这拿到了游戏思路的全部一致性收益，成本约为做一个游戏的 1%，且不改变现有架构
（仍然是"文件为事实源、引擎只是硬约束的执行者"，与 ADR-016 一致）。

### 游戏思路本身仍有价值的场景

- **支线生成器**：主线由规划控制，配角支线用游戏模拟跑出来再筛选——涌现与可控各取一半
- **日志体/直播体等文体实验**：文体本身匹配日志，映射损耗最小
- **emergent narrative 研究**：作为研究项目值得，但那是另一个目标

## 第四批：注册表体系 / 设定交代 / 分级记忆 / 跨类型适配 / prompt 组装（2026-08-30）

### 第 1 条：像游戏注册表一样引入人物/物品/地点/事件注册表？

**结论：采纳，且系统已走一半。** 游戏注册表三条核心——实体唯一 ID、ID 引用而非字符串、
登记处统一管理 + 引用完整性校验。现状审计：人物（characters.json，含 aliases/first_appear/
relationships）与地点已是注册表形态；势力半结构化（worldview.factions）；**物品/功法完全没有**
（worldstate 自由字符串）——这正是《太上忘情录》「圆满/残篇/残卷」三叫法的根源。

两个落地决策（用户拍板）：
- **items + skills 两张表**（物品=可持有实体；功法=可学习实体，语义不同，对应游戏道具表/技能表）；
- **事件注册表先不做模板库**——小说事件无"触发条件/脚本"可复用，细纲 key_events 声明清单已够。

落地：M3g（items/skills schema + core/registry.py + worldstate 引用归一化 + R-ITEM 规则）。

### 第 2 条：角色卡应像 agent 记忆——当前状态/近期记忆/长期记忆？prompt 会不会过长？

**结论：该做，但"分层注入"而非"分层全塞"。** 当前 system prompt 已实测 1500–2500 字
（随出场人物数线性涨），每人叠全部历史会直接触发思考型模型的预算问题。

- **当前状态**：全量注入，但每行必须短（worldstate 快照，已有）；
- **近期记忆**：不注入全部，按相关度检索 top-k（先忆本就是检索，不是时间窗口）；
- **长期记忆**：只存不注入，人物卡核心字段（性格/弧线/关系）代表。

增量：**写回时也分级**——plot_event 碎片带事件 type，检索按类型加权
（turning_point/reveal ×1.30、dialogue ×0.80），先忆天然偏重大事。已落地（M3g）。

### 第 3 条：物品获得是否应组装一个具体顺序？

**结论：要，但分两个地方放。** 规划期——细纲 key_events 声明"本事件系统奖励：XXX"，
奖励倒退（第 1 章圆满→第 2 章残篇）在规划期被拦；运行期——worldstate 物品按获得顺序
注入生成上下文（items 追加顺序即获得顺序），且同物异名归一化后不可能再出现"同一物品
两种状态并存"。已落地（注册表 + 归一化 + R-ITEM）。

### 第 4 条：换类型（都市高武）能否无缝衔接？

**结论：隔离度良好，一处轻度耦合已修。** 类型无关项：bible 文件结构、人物/伏笔注册表、
context 注入、编纂事件六分类、worldstate 字段名（realm/location/items 通用）、R-STATE
境界比较（层级从 worldview.power_system.levels 配置读取）。轻度耦合：编纂员状态抽取键
写死中文"修为/境界"→ 已扩展实力/战力/等级（M3g）。换类型真实成本在 bible 质量
（世界观/人物/细纲重写，取决于世界观构建师——仍缺失，B-01）。

### 第 5 条：当前 prompt 如何组装？

现状（实证）：system_prompt = context.py 九段拼接（身份/世界设定/文风/主角硬约束/出场人物/
当前状态/未回收伏笔/输出纪律/输出格式）；user = 细纲 + 记忆先忆；事件级 = 细纲目标 +
本步骤事件 + 上文接缝 300 字 + 相关前情。另有三类独立模板（编纂/审校/润色）。两个结构问题：
世界观全量进 system（不分轻重）、组装分散在 3 处无统一入口。M3g 已把"设定"改为事件级
按需注入（设定条目库），统一装配器仍待做。

## 第五批：首次介绍 / 明暗线 / 递归展开 / 审校链路（2026-08-31）

### 第 1 条：首次出现的人物/事物/组织是否也该像设定一样介绍？+ "小说起始"设计

**结论：该，但实体类型决定交代方式。** 设定/规则/组织走 settings 状态机（注入即要求
带出，缚灵司已验证）；物品/功法走注册表 + settings 式条目；**人物不硬交代**——硬交代
必然变成"陈默，男，21 岁，大二学生"说明书腔，正确载体是细纲 key_events（事件里带出
身份），或首次出场人物卡标注"通过行动/对白自然认识"（M3h 已加）。

**"小说起始"（楔子/群像开场）**：系统层面**不需要新机制**——开篇是冲突还是平淡由细纲
决定（当前三本 key_events 全写冲突是细纲写法问题，非系统限制）。楔子开场可立为细纲
模式：第 1 章第一个 key_event 写成"晨间日常"批量点亮首次交代，与冲突开场并存。

### 第 2 条：明暗线——按大纲展开能否让故事围绕线索？

**结论：当前是"细纲人工对齐"，系统无显式机制（已修，M3h）。** 审计：volumes.json 有卷
主线但不进生成上下文；plot_threads 只有登记+注入提醒，无推进/回收代码，编纂员

paid_off 自动判定与超期告警（R-THREAD）暂不做。

### 第 3 条：深度优先递归展开是否实装？

**未实装**——第二批第 2 条选择声明式 key_events 替代 LLM 递归判断。评估：3–5 章规模
声明式够用（v4 三章 16 事件、0 截断）；重场戏写厚需要"受控一层递归"（细纲标记可展开 →
一次 LLM 子事件清单 ≤3 个，深度 1 层），但优先级低于明暗线与审校闭环，暂缓。

### 第 4 条：审校 agent 审出问题后系统如何处理？能否在生成层处理？

**现状（修前）：只记录不处理。** produce_chapter 不调 Reviewer（审校完全在编排流外，
harness 生成后调用只计数）；ReviewIssue.suggestion 字段从未被使用。

**修法（M3h）**：每事件审校+修订——事件循环里每事件生成后审校该片段，block 级问题

（项目级独立文件），后续生成注入【历史教训】段（经验回灌，问题不重复发生）。
事前约束（铁律/战力/人物边界注入）保留，与事后修订互补。
