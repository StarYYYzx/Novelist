## 一、情节设计敲定过程（进入 CLI 之前）

### 1.1 一句话创意（原始输入）

> 杨铭是一名大学生，意外出车祸，穿越修仙世界，成为玄剑宗的一名普通杂役，穿越后觉醒了出名就变强系统。在某个范围内，根据自己的出名程度，无论好名还是恶名，无论真名还是化名，都可以让自己获得全方位的加强，包括修为，修炼速度，悟性等等。于是杨铭最终的目的就是名震整个世界，成为世界最强者。

### 1.2 作者-助手细化交流（分点敲定）

按 forge 构建层"作者敲定设计 → 系统据此填充世界观/角色/情节"的语义（`blueprint.provenance` 会把
作者提供的关键设定标为 `src: user`，系统自行细化部分标为 `src: llm`），本次在调用 CLI 前先与作者敲定了以下设计决策：

| # | 待定项 | 敲定结果 | 说明 |
|---|--------|----------|------|
| 1 | 作品基调 | 玄幻爽文，但文风**沙雕搞笑、轻松吐槽** | 与 cliché 严肃修仙区分开 |
| 2 | 系统是否有阴谋暗线 | **纯爽，无幕后阴谋暗线** | 系统迷团不在本卷开启（即便如此，系统据此仍漂移出 `ln:system_mystery`，见 §4.3） |
| 3 | 主角刷名声策略 | **双名策略**：真名行善刷正名 + 化名暗地教训恶人刷恶名，正恶双修 | 吃满系统"无论好名恶名"设定 |
| 4 | 卷主线与节奏 | 宗门崛起初段·杂役扬名；进度不快 | 穿越觉醒→首次小规模扬名树小敌→马甲线启动、正恶双修成型→危机升级疑似马甲曝光→阶段收束、埋升级钩子 |

> 注：系统设计本支持**分轮商讨协议**（`forge/ask` + 终端通道 `io_console`，`docs/10`）。
> 本次测试采用 `--mode auto`，把上述已敲定的设计**一次性固化进 brief 注入**，跳过逐轮 ask，
> 以便聚焦正文生成链路；全文交流记录见 §4（transcript）。两种模式的区别在此如实说明。

## 二、完整命令序列（按执行顺序）

> 环境：Windows PowerShell 5，托管解释器 `C:/Python314/python.exe`（pytest 9.1.1）。
> 每次调用前统一设置 `$env:PYTHONPATH="e:\360MoveData\Users\Administrator\Desktop\novelist\src"`。
> 工作目录：`e:\360MoveData\Users\Administrator\Desktop\novelist`。

### 阶段 A：初始化项目

```powershell

C:/Python314/python.exe -m novelist.cli init "e:\360MoveData\Users\Administrator\Desktop\novelist\novel_workspace" --title "出名就变强"
```

产物：`novel_workspace/proj-20260906201649/`（含 project.json、workspace 骨架）。

### 阶段 B：种子提炼（forge seed）

```powershell

C:/Python314/python.exe -m novelist.cli forge seed "《出名就变强》一句话创意：杨铭是……（§1.2 完整固化版，含全部 8 项敲定设计）共需撰写5章。" "novel_workspace/proj-20260906201649" --provider deepseek --mode auto --volumes 1 --chapters-per-volume 5 --target-words 1000 --max-calls 150

> 位置参数即一句话创意（要点见 §4.1 的 `seed.start` 记录）。`--mode auto` = 跳过人工分轮商讨。

### 阶段 C：审批 6 大核心模块（永久放行）

```powershell

```

各模块产物见 `workspace/forge/reviews/*.md`（§4.2）。`--remember` 表示该模块后续不再审核。

### 阶段 D：forge build（产出 bible + 大纲 + 卷纲/章纲）

```powershell
$env:PYTHONPATH="e:\360MoveData\Users\Administrator\Desktop\novelist\src"
C:/Python314/python.exe -m novelist.cli forge build "novel_workspace/proj-20260906201649" --provider deepseek --max-calls 150
```

> 首次我用 `build --dir <dir>` 因不识别 `--dir` 退出码 2；改回**位置参数目录**即成功。
> build 分多轮执行：每产出一批模块会在审核闸门处暂停，处置完后重新 `build`（同命令）续跑。

### 阶段 E：卷纲 / 章纲审批闸门

```powershell
$env:PYTHONPATH="e:\360MoveData\Users\Administrator\Desktop\novelist\src"
C:/Python314/python.exe -m novelist.cli forge approve outline_volume  --remember --dir "novel_workspace/proj-20260906201649"
C:/Python314/python.exe -m novelist.cli forge approve outline_chapter --remember --dir "novel_workspace/proj-20260906201649"
```

> 注意：**审批闸门子命令用 `--dir`**，而 build/seed/chapter 用位置参数目录，二者参数形态不同。
> 每次审批后再 `forge build ...`（同阶段 D 命令）拉取下一段构建。

### 阶段 F：逐章生成正文（chapter，direct 直出模式）

```powershell
$env:PYTHONPATH="e:\360MoveData\Users\Administrator\Desktop\novelist\src"
C:/Python314/python.exe -m novelist.cli chapter "novel_workspace/proj-20260906201649" --vol 1 --ch 1 --provider deepseek --direct --event-loop --seam-review --volume-facts --gen-tokens 4000
```

同样的命令把 `--ch N` 从 1 改到 5 逐章执行。

> **重要**：前两次我用**默认 tool 模式**（不带 `--direct`）暴露了缺陷 DA（草稿不落盘，见 §5.1）。
> 改带 **`--direct`** 后，正文经 `ws.write_text` 直接落盘，正常产出 5 章草稿。

## 五、发现的问题

### 5.1 DA — 真实 DeepSeek tool 模式下正文草稿不落盘（严重）

**现象**：不带 `--direct`（默认 tool 模式）跑 `chapter`，两次运行（后台 2028字 / 前台 2703字）
`drafts/chapters/1-1.md` 均未写入磁盘，但 reports、memory、`.index.db` 等照常落盘，且日志仍显示
`wrote draft … completeness ok`。

**定位**：用 `ScriptedProvider`（隔离、零 LLM 成本）在真实项目目录下复现 produce_chapter →
**草稿正常落盘**，证明系统代码/路径/环境均正常。差异仅在**真实 DeepSeek 会话**：tool 模式下正文由
Agent 循环的 `write_draft` 工具落盘（F2 修复后工具模式不再把结束语 final 写草稿），而真实运行时
**该工具并未被实际调用**，正文只存在 Agent 结束语里 → 草稿为空，但记忆/审计照常、完整性仍显示 ok。

**规避**：改用 **`--direct`** 直出模式（orchestrator 用 `ws.write_text` 直接落盘），绕开工具调用即可正常产出 5 章。

**建议**：回填 `docs/问题总账-2026-09-03.md` 待修（真实运行时若 tool 未产出草稿应给出明确告警或兜底）。

### 5.2 环境注意 — TRAE 文件视图缓存不一致

排障中多次出现 `Get-ChildItem`/`Read` 误报"文件不存在"或显示幽灵列表（例如 `chapters/` 目录列出一堆 1-N.md
但实际为空，或被标注不存在的 `1-5.md` 却能列出）。**以 python `os.path.exists`/`os.listdir` 在真实磁盘核验为准**。
此环境问题曾二次造成"草稿丢失"误判（实际草稿一直在磁盘）。
