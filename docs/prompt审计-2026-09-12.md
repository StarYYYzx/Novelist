# 第一部分 · 技巧基线（只留有实证支撑的）

每条标注 **核验状态**：`已核验`= 本次打开原文/一手来源；`厂商文档`= 官方文档内容（本次未逐条打开）；`社区经验`= 无硬数据。
`【小说适用性】` 标记创作场景的特殊处理。

## 1. 位置效应：U 型曲线（最高置信度，直接适用）

- **结论**：相关信息放在**开头或结尾**表现最好，放**中间**显著下降；上下文越长越差。
- **依据【已核验】**：Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*, TACL 2023, [arXiv:2307.03172](https://arxiv.org/abs/2307.03172)。原文：GPT-3.5-Turbo 在 20/30 文档设置下，答案放中间时性能**低于不给任何文档的闭卷基线（56.1%）**。原文明确指出该现象**跨任务类型成立**（多文档 QA 与 key-value 检索同形）。
- **重要边界**：该论文自述局限——只在 QA 与键值检索上做实验，**未测创意写作**。所以「U 型曲线适用于小说正文生成」是外推，不是该论文的直接结论。但下面的第 2 条（缓存）与第 3 条（矛盾指令）**不依赖这个外推**，是本项目可独立验证的。
- **可操作**：硬约束（红线/禁令/输出格式）放 prompt 首尾；技法类建议沉底；大面积引用材料放中段。

## 2. Prompt caching：前缀逐 token 一致才命中（本项目最大成本杠杆）

- **结论**：缓存**按前缀匹配**——「从第 0 个 token 开始完全一致」才命中，**中间重复不算**。稳定内容必须前置，动态内容必须后置。
- **依据【已核验】**
  - DeepSeek 官方口径：DeepSeek API 采用**上下文硬盘缓存**，**无需改代码、自动运行**；「只有当两个请求的前缀内容相同时（从第 0 个 token 开始相同），才算重复。**中间开始的重复不能被缓存命中**」。
  - DeepSeek 2026-09-10 12:00 起生效的 Flash 系列新价（多来源一致）：**空闲时段 缓存命中输入 0.02 元/百万 token，缓存未命中输入 1 元/百万 token**——**价差 50 倍**；高峰时段（工作日 9:00–12:00、14:00–18:00）各项翻倍。（输出单价各来源口径有出入：2 元 vs 4 元，需以官方价目页为准；不影响本条结论。）
  - 来源：DeepSeek 官方公众号《DeepSeek API 创新采用硬盘缓存》；[阿里云开发者社区解读](https://developer.aliyun.com/article/1762718)；[新浪财经报道](https://finance.sina.cn/2026-09-09/detail-inirfqcs5659028.d.html)。
  - 缓存脆弱性【已核验】：Anthropic 官方文档明确把「**在静态 system prompt 里放一个详细的 timestamp**」列为**破坏缓存的常见原因**之一；并给出实践数字「缓存命中率从 70%+ 掉到 7%」。[Prompt caching 文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)；[Claude Code: Prompt caching is everything](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)（92% 命中率来自「静态前缀 / 动态尾部」的干净分层）。
- **可操作**：system prompt 里**不放任何逐章/逐次变化的内容**；把章节号、时间戳、当前任务全部移到 user message。

## 3. 创意写作场景的 CoT：无明显收益，可能有害

- **结论**：CoT 在数学/符号推理上收益明确；在**创意文本**上收益小、不显著，且**提升连贯性的同时降低指令遵循**。
- **依据【已核验】**
  - Morain & Ventura, *Is Prompt Engineering the Creativity Knob for LLMs?*, ICCC 2025 —— 系统比较 basic / human-engineered / 自动优化(OPRO) / CoT 四种策略，覆盖笑话、诗、六词小说、微型小说四个域，**人类问卷 + GPT-4o 自动评估**。结论：**「OPRO 和 R1 这类先进提示技术，产出物的质量、新颖性、创造性并不显著优于基础提示」**。[论文 PDF](https://computationalcreativity.net/iccc25/papers/iccc25-morain2025prompt.pdf)
  - IJSAT 2025 提示工程权衡研究：创意写作上「提示带来的增益统计显著但很小且不稳定，且**只改善连贯性而非指令遵循（compliance）**」；「连贯性、长度与复杂度提升余弦相似度但**降低任务遵循**」。[论文 PDF](https://www.ijsat.org/papers/2025/2/2584.pdf)
- **注意置信度**：这两篇用的是 GPT-4o / Llama / R1 一代模型，未测 DeepSeek-V4-Flash。结论方向可信，**幅度不可外推**。
- **【小说适用性】** 本项目当前口径（正文生成 `thinking=False`、判断类 `thinking=True`）**与这条建议一致，无需改动**。但要警惕：不要为了「让模型想清楚」而给正文生成开思考——那既烧输出预算又可能伤文风。

## 4. 结构化输出：JSON mode ≠ schema 约束

- **结论**：`response_format=json_object` 只保证**可解析**，不保证**形状**；形状必须由应用层校验 + 修复回路兜住。
- **依据【厂商文档】**：OpenAI 明确区分 JSON mode（仅保证合法 JSON）与 Structured Outputs（保证符合给定 schema）。DeepSeek 的 `json_object` 属前者，且有额外约束——**prompt 里必须出现 "json" 字样**，否则 400。
- **本项目已部分采纳**：31 个调用点里 13 个要求 JSON，其中 12 个设了 `response_format="json_object"`；`forge/validate.py` 做了契约校验。**唯一漏网点见 P1-5。**

## 5. Few-shot：创意场景的最高杠杆

- **结论**：示例的**质量**比数量重要；3–5 个相关示例收益最高；**负面示例（Wrong/Right 成对）对修正固定错误有效**；正面示范通常比负面禁令有效。
- **依据【厂商文档 + 社区经验】**：Anthropic prompt library 推荐 3–5 个示例【厂商文档】；「粘贴两段真实样本文本总是有效」属实践共识【社区经验，无厂商硬数据】。
- **【小说适用性】** 这条在小说场景**比通用场景更重要**——因为情节/设定可以靠结构化数据约束，**文风只能靠示范**。当前项目对文风的约束只有 `tone/pov/tense/narration` 四个形容词式字段 + 37 条禁用词，全是负面的。**见 P1-3。**

## 6. 反模式清单（本项目命中项已标 ✗）

1. 全大写/加粗强调过多 → 噪声 ✗（**实测 system prompt 里 `**不要**`/`**必须**` 密度高**）
2. **过长禁令列表（>10 条）→ 模型抓不住重点** ✗（**实测 38 条禁用词**）
3. 矛盾指令（同一 prompt 内两说）✗ **见 P0-2**
4. 要求"完美/零错误" —— 本项目未见，好
5. schema 说明塞最后 —— 本项目把 `_protocol_block` 放 user 末尾，**落在 recency 位，属有利**，不判定为问题
6. 单 prompt 混多任务 —— 本项目已大幅拆分（细纲/正文/审校/润色分调用），好
7. 长素材塞中部 ✗ **见 P1-1**
8. system prompt 堆人格小传 —— 本项目反过来（人格极简），好
9. 只写"返回 JSON"无 schema ✗ 部分（形状靠 prompt 文字描述 + `forge/validate.py` 兜）
10. 改 prompt 无版本/golden 集 ✗ **见 P1 通项**
11. 对正文生成强加 CoT —— 本项目未犯，好
12. 每次重发相同长上下文却不组织前缀 ✗ **见 P0-1（最严重）**

# 第三部分 · 差距分析（每条给证据 + 修法）

## P0-1 · system prompt 第一行含章节号 → 缓存命中率结构性为 0

**证据**

`core/context.py:164`：

```python
L.append(f"你是一部{genre or ''}长篇小说的主编剧，正在写第 {vol} 卷第 {ch} 章。")
```

这是 system prompt 的**第 0 行**。实测（`novel_workspace/_harness/prompt-audit-2026-09-12-sysprompt-fame5.txt`）第 1 行就是它。

- DeepSeek 缓存规则（官方，已核验）：**必须从第 0 个 token 起前缀一致**。第一行含 `vol/ch` → **每章前缀都不同** → 后续 2600+ 字全部 miss。
- 更糟的是同一章内的**每次调用**：`_generate_with_continuation`（`orchestrator.py:481`）等生成调用都带同一 system prompt，但**每章都要重建前缀**。
- 实测用量（77 章真实审计）：**输入中位数 39,079 tokens / 输出中位数 18,280 tokens**，输入:输出 = **2.64 : 1**。输入是大头。
- 实测单章调用数 **23–43 次**（fame5 后期章），每次都带 system prompt。
- 价差（DeepSeek 2026-09-10 起）：命中 **0.02** vs 未命中 **1** 元/百万 → **50 倍**。

**顺带发现（同一条根因的下游）**

- `core/llm.py:76-80` 的 `Usage` 只有 `tokens_in/tokens_out/reasoning_tokens`，`providers/openai.py:186-190` 也只读 `prompt_tokens`/`completion_tokens`。**没有采集 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`**（DeepSeek 在 `usage` 里返回这两个字段）。
  → **本项目无法测量自己的缓存命中率**。而这是 DeepSeek 新定价下唯一决定成本的指标。
- `orchestrator.py:1335`：`cost = counter.tokens_in / 1e6 * 1.0 + counter.tokens_out / 1e6 * 2.0` —— 价表是旧的、且**不区分命中/未命中**，成本报告系统性失真（低估未命中、无法体现命中收益）。

**修法（改动极小）**

1. `context.py:164` 改为常量前缀，例如 `你是本长篇小说的主编剧。`；章节号本来就已在 user goal 里（`context.py:330`：`请撰写第 {vol} 卷第 {ch} 章正文。`），**删除是纯冗余消除，不损失任何信息**。
2. `Usage` 增 `cache_hit_tokens` / `cache_miss_tokens`；`openai.py` 从 `usage` 读取。
3. `_write_generation_audit` 价表集中成常量，按命中/未命中分别计费，报告里输出**命中率**。

**预期收益**：system prompt 那部分输入从「未命中价」降到「命中价」，且章节内所有调用的 system 前缀变成**全书一份**。改动 3 处、约 15 行，**无行为风险**（章节号在 user 里已有）。
**验证**：重跑一章，对比 `usage` 里新增的两个字段；命中率应接近 system prompt 占输入的比例。

## P0-2 · 同一 prompt 内自相矛盾的标题指令（真 bug）

**证据**

`core/context.py:32-34`：

```python
DISCIPLINE = [
    ("元叙事", "正文里不得出现「第X章」「本章」…章节标题只在第一行出现一次。"),
    ...
]
```

`core/context.py:285-291`（event_loop 分支）：

```python
if event_loop:
    # H8 修复（2026-09-05）：事件循环下每事件 discipline 要求"不要写章节标题"，
    # system 却要求"第一行写标题"——同场矛盾指令是事件边界复读标题的成因之一。
    L.pop()
    L.append("【输出格式】…**不要写章节标题**、不要写「第X章」字样…")
```

**H8 只修了一半**：event_loop 分支只替换了【输出格式】那一行，**没有动 DISCIPLINE**。

**实测验证**（fame5 V1C3 导出，`event_loop=True`）：

```
【输出纪律】
- 元叙事：…章节标题只在第一行出现一次。          ← 说"要"
【输出格式】直接输出正文片段。**不要写章节标题**…   ← 说"不要"
```

同时 `orchestrator.py:967` 事件级 discipline 也是「**不要写章节标题**」。→ **2 处说不要，1 处说要在第一行出现**。这正是代码注释里自己诊断出的成因，却没有修完。

**修法**：`DISCIPLINE` 的「元叙事」条按 `event_loop` 生成两个版本；或把「章节标题只在第一行出现一次」从 DISCIPLINE 摘出，只在非 event_loop 的【输出格式】里说。

**验证**：`build_system_prompt(..., event_loop=True)` 的输出中不应再出现「章节标题只在第一行出现一次」——可直接写进既有 `tests/`（源码级守卫，与 `test_batch2_adb` 同类）。

## P0-3 · 禁用词表：38 条 + 精确重复（维度 H FAIL）

**实测**（fame5 V1C3）：

```
- 禁用词，出现即失败：打卡、手机、网络、系统崩溃、CPU、GDP、键盘、穿越、重生、
金手指、外挂、无敌、震惊、倒吸一口凉气、心中一震、喃喃自语、嘴角勾起一抹、
意味深长、不得不、不禁、仿佛、如同、就像、似乎、大概、也许、可能、或许、总之、
综上所述、总而言之、由此可见、显而易见、毫无疑问、毫无疑问地、毫无疑问的、
毫无疑问地、毫无疑问的
```

程序化统计：**38 条**，其中 `毫无疑问地` ×2、`毫无疑问的` ×2 = **精确重复 2 条**（去重后 36）。加上 `毫无疑问` 本体，「毫无疑问」这一族占 5 条。

**两个独立问题**

1. **维度 H（规则去重）FAIL**：`毫无疑问地`/`毫无疑问的` 各出现两次，属「同一格式完全重复」。根因不在渲染侧（渲染是 `'、'.join(banned)`），在 **forge 生成 `style.forbidden_words` 时未去重**。
2. **反模式 #2**：38 条禁令远超「>10 条模型抓不住重点」的经验阈值。研究给出的替代是**负面示例（Wrong/Right 成对）**而非长词表。

**修法**
- 装配侧确定性兜底：`dict.fromkeys(banned)` 去重（一行，零风险）+ 上限截断（如 ≤15，超限写 WARN 到构建报告）。
- forge 侧生成 `forbidden_words` 后做同义归一（「毫无疑问」族合并为 1 条）。
- 中期：把长词表降级为 **polish 的后置过滤**（`polish.py` 已有 9 信号确定性度量做这件事），给正文生成的禁令收缩到 5–8 条最高频的。

## P0-4 · 专有名词表：同 term 重复渲染 + 空壳条目

**实测原文**：

```
- 专有名词（写法必须固定）：【出名就变强系统】、声望值、明善暗恶（）、
声望值（系统核心货币，…）、双圣（…）、【出名就变强系统】（主角绑定的核心辅助机制，…）、
明善暗恶（主角的核心人设标签。…）、权限不足（…）、数据异常（…）
```

三处问题：

| 现象 | 具体 |
|---|---|
| 同 term 重复 | `声望值` ×2（一次无 note、一次有 note）；`【出名就变强系统】` ×2（同形） |
| 空壳渲染 | `明善暗恶（）` —— note 为空时仍渲染括号，占位且无信息 |
| 顺序 | 「骨架条目」在前、「详细条目」在后，模型读到的第一个是**信息量最低的那个** |

**修法**：`context.py:233-235` 渲染前按 `term` 归并（后者覆盖前者，或note 取长者），note 为空则不渲染括号。

**问题**：1343 字的工艺卡（全文 50%）压在 **34%–84%** 区间——按 U 型曲线，这是注意力最低的中段。而它的内容里有 4 处标注「**硬约束**」（系统呈现规范 / 单章节奏规范 / 伏笔与暗线规范）。

1. 红线类（`forbidden_words` / `modern_words` / 输出纪律 / 输出格式）→ **首尾**
2. 硬设定（主角硬约束 / 人物名单 / 境界体系）→ 前段
3. 工艺卡 → 后段（输出格式之前）
4. 世界设定 / 本卷主线 → 中段

## P1-3 · 全书零文风示范（few-shot 缺失）——创作侧最高杠杆

**证据**：`schemas/bible/` 下 `style` 契约字段为 `pov / tense / narration / tone / target_words_per_chapter / forbidden_words / modern_words / glossary / protagonist / craft_cards`。**没有任何目标正文样本字段。** 全部 31 个调用点扫描：**0 处 few-shot**。

**为什么这是最重要的创作侧缺口**：情节一致性可以靠结构化数据（人物卡/实况状态/线索卡）约束，**文风只能靠示范**。当前对文风的全部约束是：4 个形容词式字段（`严谨冷肃`/`诙谐幽默`/…）+ 38 条禁用词 + 8 条「必须消除的 AI 腔调」——**全是负面的**。而研究结论是「正面示范 > 负面禁令」，且 `polish.py:296-331` 的 `TONE_TEMPLATES` 本身就是用形容词描述风格（「句式短促克制，多用陈述句与冷峻动作」），这类描述的可执行性远低于一段真实样本。

**修法**
1. `style.json` 增 `exemplars: [{text, source, note}]`（3–5 段**人工认可**的目标文风文本，建议取自本项目已定稿且人工审读通过的章节片段，而非外部小说——避免风格与设定不符）。
2. 注入到两个位置：正文生成的 system prompt（靠近输出格式，recency 位）+ `polish.py` 的 `build_polish_prompt`。
3. 与 `craft_cards` 同理，控制总量（3–5 段 × 200–300 字 ≈ 600–1500 字），并纳入 `prompt_budget` 可淘汰层。
4. 配 `docs/` 说明样本来源与授权（避免版权问题）。

**注意**：这条是**新增能力**，不是修 bug。需要用户拍板是否引入（涉及数据准备与风格口径）。

## P1-4 · 「防重复」纪律散落 5 处

**实测**（事件 prompt，22 块）：

| 块 | 位置 | 原文 |
|---|---|---|
| 4 输出纪律 | 前 | 不要重复上文已经写过的内容 |
