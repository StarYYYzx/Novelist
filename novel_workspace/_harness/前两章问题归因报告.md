# 前两章问题归因报告（v6 / 3080ti / Qwen3.5-9B 关思考）

> 输入：用户人工审读 ch1（`1-1.md` 9682 字）、ch2（`1-2.md` 4026 字）后的 5 类批评
> 方法：逐条比对 正文 ↔ 细纲 `outline/chapters/1-{1,2}.md` ↔ bible `characters.json`
>      ↔ 日志 `run_v6_log.jsonl` ↔ 生成链路代码
> 结论口径：每个批评都定位到**具体代码行**，并区分「流程缺陷 / 模型能力 / prompt 缺陷 / 其他」

---

## 0. 结论速览

**一句话**：用户看到的所有"拼接感"症状，**不是模型随机犯错，而是同一条确定性缺陷链的三种外显**——
「事件超写 → max_tokens 截断在半句 → 续写 → 续写时模型重写章节标题并复述接缝 →
拼接无分隔符 + 去重只扫开头 12 句 → 标题内联、段落重复」。

| 归因类别 | 占比（估计） | 是否可工程修复 |
|---|---|---|
| **A. 流程设计问题** | **~65%** | ✅ 可修，且多数是低成本确定性修复 |
| **B. 9B 模型能力上限** | ~20% | ❌ 换模型才能根治（27B / API 强模型） |
| **C. prompt 设计问题** | ~10% | ✅ 可修 |
| **D. 其他（配置/数据）** | ~5% | ✅ 可修 |

**最关键的意外发现**：`completeness()` **完全没有重复段落检测**（polish.py:108-122 只查元叙事且跳过首行），
所以 4 次「且看谁先沉不住气」、2 次「青云宗，我来了」这类硬伤**系统自己一张告警都没报**，
与 v5 评阅的判断一致——**0 告警 ≠ 没问题，只是没检查**。

## 1. 决定性证据：三段标题的位置揭示了整条缺陷链

| 行号 | 原文（截断显示） | 形态 |
|---|---|---|
| 1 | `## 第 1 章 魂穿杂役院` | ✅ 行首（正常，来自事件 1 首次生成） |
| **111** | `…心中却在默默祈祷，希望这个系统## 第 1 章 同频之秘` | ❌ **正文半句 + 标题内联** |
| **195** | `…心中不禁涌起一股豪情。若能在此## 第 1 章 听风谷的"五五开"` | ❌ **正文半句 + 标题内联** |

行 111 / 195 的形态**不可能**由事件间拼接（`"\n".join`，orchestrator.py:1211）产生——那样标题必然在行首。
唯一能产出「半句紧挨 `##`」的代码路径是**续写拼接**：

```python
# src/novelist/core/orchestrator.py:209
text = text.rstrip() + strip_seam_overlap(text, piece)   # ← 无任何分隔符
```

`text` 结尾是半句（被 `finish_reason="length"` 截断），`piece` 开头是续写模型重写的新标题 `## 第 1 章 …`，
直接相加 → `…希望这个系统## 第 1 章 同频之秘`。**与原文逐字吻合。**

### 实证复现（不是推断，是在真实代码上跑出来的）

```python
>>> from novelist.core.orchestrator import _dedupe_chapter_titles, strip_seam_overlap

# ① 标题去重对 ch1 彻底失效
>>> _dedupe_chapter_titles(ch1)
[1-1] 标题数 处理前=3 处理后=3   → 失效（只删掉末尾 1 个换行符）

# ② 续写接缝去重：prev=被截断的半句，piece=续写内容（重写标题+复述接缝）
>>> strip_seam_overlap(prev, piece)
'## 第 1 章 同频之秘\n\n叶岚心中却在默默祈祷，希望这个系统能在他被识破之前…'
标题是否被去除: False
接缝复述是否被去除: False

# ③ 按 209 行的方式拼接，得到与原文行 111 完全一致的结果
>>> prev.rstrip() + out
'…心中却在默默祈祷，希望这个系统## 第 1 章 同频之秘\n\n叶岚心中却在默默祈祷…'
```

**三道防线逐道失守**：续写去重没拦住 → 拼接没加分隔符 → 标题去重只认行首。
注：② 中即便剥离标题，句级相似度仍只有 ~0.29（该句仅前 30% 是复述、后 70% 是新内容），
现有 `sim=0.70` 阈值判定不出——**这解释了为什么单纯调阈值也救不了，必须改结构**。

## 3. A. 流程设计问题（~65%，主因）

### A1. 续写拼接无分隔符 —— 标题内联的直接元凶 ★最高优先

```python
# orchestrator.py:205-209
piece = (res.content or "").strip()
if not piece:
    break
text = text.rstrip() + strip_seam_overlap(text, piece)   # ← 缺 "\n" 或 "\n\n"
```

**后果**：标题与半句粘连成一行 → `_dedupe_chapter_titles` 的 `^#{1,6}\s*第…章`（orchestrator.py:846，`re.match` 行首锚定）永久失效。
该函数本身设计是对的（甚至注释里就写了「实测诡夜大学 ch1 的 3 事件重题」），**但只防住了事件间，没防住续写内**。

**修复**：拼接处插入 `"\n\n"`；`_dedupe_chapter_titles` 的 `match` 改 `search`（行内任意位置命中即删，保留首个）。

### A2. 去重窗口过窄 —— 段落整段重复的元凶 ★最高优先

```python
# orchestrator.py:161
if i < scan_sents and dropped < scan_sents and len(s_strip) >= min_sent:   # scan_sents=12
```

- 只扫描 **piece 开头 12 句**。
- 实测重复位置：ch1 重复「青云宗，我来了」在 **第 35-45 行**（事件 1 内部中段）；
  ch2「且看谁先沉不住气」在 **行 67 / 101 / 113 / 137**，其中后三次都在片段中后部。
- **窗口覆盖不到 → 一律放行。**

**修复**：去重从「开头 12 句」升级为「全片段滑窗查重」——对 piece 的**每一句**判断是否已出现在「已写全文」中（精确包含 or n-gram ≥ 0.85），命中即删。这是纯确定性字符串操作，零 LLM 成本。

### A3. 没有「本章已确立事实」回注 —— 设定矛盾、谎言不自洽的元凶

事件循环里，事件 N 的 prompt 只有：
- 细纲本事件文本
- 上文接缝（尾部 N 字）
- 相关前情（先忆）
- RAG 检索到的知识行

**没有**「本章前几个事件里已经发生/已经说过的事实清单」。于是：
- 事件 1 让叶岚对云清瑶说「迷魂草 + 筑基丹残液」，事件 2 对李慕白说「回春草」——**两个事件各自编，互不通信**。
- 系统规则在事件 1 是「接触即绑定」，事件 2 变成「弹窗询问是/否」——**细纲只写了前者，后者是模型自由发挥**。

**修复**：事件 N 生成后，用 Chronicler 已产出的结构化事件（`chronicler.run` 每事件都跑）累积一张**本章事实表**，
注入事件 N+1 的 prompt。数据已有，只差接线。

### A4. 人物性格对模型不可见 —— 何远/李慕白人设崩塌的元凶

```python
# context.py:214-219  system prompt 里的人物名单
names = "、".join(f"{c.get('name','?')}（{((c.get('power') or {}).get('level') or '?')}）" for c in cast)
L.append(f"【人物名单】…（本事件相关人物的性格/弧线卡片见本事件提示）：{names}")
```

设计意图是「system 不全量塞卡，改由 RAG 按事件相关性注入」（讨论第 8 轮）。**但**：
- RAG 检索的查询是 **事件文本**（`knowledge.plan_queries(ev_text, ...)`，orchestrator.py:1104）。
- 事件 1 文本是「叶岚在杂役院柴房醒来…」，**检索不到何远** → 何远的 `core_traits: ["憨厚","重义"]`、`arc: "杂役院同伴，叶岚的普通人锚点"` 从未进入上下文。
- 模型手里只有「何远（炼气二层）」六个字 → 自由发挥成带人闯听风谷的嚣张反派。

bible 数据是对的，卡也在，**只是从未被送到模型眼前**。

**修复**：对**本章已在场的实体**（worldstate 有 location 记录 / 前文已出场）无条件注入完整性格行，不依赖 RAG 命中。

### A5. 润色环节脱离 bible 约束 —— 「本小姐」的元凶

```python
# polish.py:255-263
res = llm.complete(LLMRequest(
    messages=[LLMMessage(role="user", content=build_polish_prompt(text, before, tone=tone,
                                                                  is_chapter=is_chapter))],
    max_tokens_out=max_tokens,
    temperature=0.6,          # ← 高于生成温度
))
```

**只有 user message，没有 system prompt**。于是润色时：
- 【主角硬约束】性别（context.py:196-201 明明写着「性别男，人称代词一律用「他」，绝不可混用」）→ **不生效**
- 【人物名单】防造人 → **不生效**
- 【文风约束】【输出纪律】【输出格式】→ **全部不生效**

而且润色是**整段重写 + temperature 0.6**（高于生成温度），是全程约束最弱、自由度最高的一次调用。
ch2 日志 `"polish_applied": true`，「本小姐」出现在 ch2 行 27。

> **严谨性说明**：「本小姐」无法 100% 锁定为润色引入（生成环节同样可能出错，9B 本就会犯错）。
> 但可确定的是：**润色环节是全流程唯一完全没有 bible 约束的 LLM 调用**，
> 且它会整段重写已生成文本——即便错误来自生成，润色也是**唯一有机会纠正却没有任何纠错依据**的环节。
> 无论哪种情况，透传 system prompt 都是必做项。

**修复**：`polish_chapter` 增加 `system_prompt` 参数，调用方把 `build_chapter_context` 的产物透传进去。

### A6. `completeness()` 不查重复 —— 硬伤漏网的元凶

```python
# polish.py:108-122
def completeness(text: str) -> dict:
    # 元叙事只查正文，跳过第一行——那一行是章节标题
    ...
    "meta_narration": sorted(set(meta)),
```

检测项只有：结尾完整性、长度、元叙事。**没有重复段落检测，没有跨事件一致性检测。**
ch1 日志 `meta: ["第 1 章"]` —— 元叙事检测**命中了**「第 1 章」（因为行 111/195 内联标题被当成正文），
但只记录不处理，章照发。

**修复**：新增 `repeated_spans` 检测（n-gram 自相似），命中即计为 `problems`，触发修复重试或至少落告警。

### A7. 事件越界无收敛

`_event_goal` 写了「不要写本章其他事件的内容，写到本事件结束即停」（orchestrator.py:501），
但对 9B 无效：事件 1（细纲「柴房醒来」≈300-600 字）实际写了 **3000+ 字**，
一口气把系统激活、绑定云清瑶、陈松对峙全写完了；事件 2、3 只好重写同一批场景。

**修复**：事件级也接 `length_cap_chars`（单事件上限，如 900 字）；越界后不是续写，而是**截断到句子边界 + 丢弃余下**（余下本就属于后续事件）。

## 4. B. 9B 模型能力上限（~20%）

以下问题**换 prompt 也难改**，属模型能力约束：

| 现象 | 能力缺口 |
|---|---|
| 不遵守「篇幅约 300–600 字」（超写 5 倍） | 指令遵循弱，尤其数量约束 |
| 不理解「金丹首席应有傲慢与城府」（李慕白轻易收书童） | 缺少社会层级/权力距离的隐含常识 |
| 不会写「主角刻意改口的算计」（谎言对不上却不自知） | 无跨段落意图规划能力 |
| 续写时重写标题并复述前文 | 长上下文接缝处理能力弱 |
| 云清瑶「察觉灵力完全一致却轻信走火入魔」 | 因果推理深度不足 |

**这批问题只能靠换模型**：云端已有 `Qwen3.5-27B-Q4` 备用，或走 DeepSeek API。
v6 评阅已判定「AI 味天花板未动」，与此处结论同源。

## 5. C. prompt 设计问题（~10%）

1. **润色 prompt 无 system 约束**（polish.py:255）——已归入 A5，但本质是 prompt 装配缺陷。
2. **「不要重复已有内容」只写在续写 prompt 里**（orchestrator.py:199），对 9B 无效；
   代码注释自己也承认「prompt 里写了『不要重复』对 9B 无效，只能做确定性去重」——**但去重实现又不完整**。
3. **`_event_goal` 缺少「本事件禁止出现的实体/场景」负向约束**，只有「必须带出的设定」（setting_lines）。
4. **细纲粒度不足**：`key_events` 只有一句话（如「陈松克扣灵石，叶岚借筑基气息震慑全场」），
   没有指定**场景**、**出场人物**、**结局状态**，给模型留了过大的自由空间。

## 8. 验证方法

修复后重跑 ch1-2，用确定性指标验收（不依赖主观阅读）：

```python
# 重复段落检测：60 字滑窗自相似
def max_repeat(text, n=60):
    seen, worst = {}, 0
    for i in range(len(text) - n):
        g = text[i:i+n]
        if g in seen: worst = max(worst, n)
        seen[g] = i
    return worst

# 验收阈值
assert count_headings(draft) == 1                    # 标题唯一
assert max_repeat(draft) < 60                        # 无 60 字以上重复
assert "本小姐" not in draft                          # 性别一致
```

## 9. 一句话总结

> **用户看到的是"多份草稿未整合"，实际是"一份草稿被续写了两次、每次都从标题重新开始，
> 而去重逻辑只检查开头 12 句、标题检查只认行首、润色环节完全没有 bible 约束、
> 最后一道完整性校验根本不查重复"。**
> 六道防线的每一道都恰好漏过了这一类问题——这是流程缺陷，不是模型随机犯错。
